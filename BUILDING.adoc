== Prerequisites

* CMake >= 3.30, Ninja and a C++26-capable compiler/standard library.
* Firmware: ARM GCC (`arm-none-eabi-g++`) and its binutils on `PATH`.
  The supplied toolchain is `cmake/arm-none-eabi-gcc.cmake`.
* Host tests: GCC or Clang and Python 3. The SDL3 simulator additionally needs
  SDL3 development files and a POSIX host.
* CMSIS headers are fetched at configure time from pinned upstream versions.
  No STM32 HAL or vendor startup code is used. See <<offline>> for local sources.

Run the following commands from the CoreTX repository root.
Use separate host and firmware build directories.

== Firmware builds and artifacts

[source,shell]
----
cmake --preset i6x
cmake --build --preset i6x
cmake --preset i6s
cmake --build --preset i6s
----

Each board build produces both English and German menu images:

[cols="1,2,2",options="header"]
|===
|Board |English BIN |German BIN
|FS-i6X |`build-i6x/coretx-i6x-en.bin` |`build-i6x/coretx-i6x-de.bin`
|FS-i6S |`build-i6s/coretx-i6s-en.bin` |`build-i6s/coretx-i6s-de.bin`
|===

The matching `.elf`, `.hex`, `.map` and `*-resource-report.txt` files support
debugging and flash/RAM inspection. The raw BIN starts at *`0x08000000`*.
The linker enforces 128 KiB flash, 16 KiB SRAM and a reserved 2 KiB stack;
optional features must still fit these limits.
The source firmware version is set in `coretx/version.hpp`.

Only build one language when desired:

[source,shell]
----
cmake --build --preset i6s --target coretx-i6s-en
----

i6S diagnostic targets are excluded from the default build:

[source,shell]
----
cmake --build --preset i6s --target coretx-i6s-touch-trace
cmake --build --preset i6s --target coretx-i6s-touch-diagnostic
cmake --build --preset i6s --target coretx-i6s-measurement
----

`touch-trace` is the full firmware with extra touch diagnostics and additional
resource use. `touch-diagnostic` is a standalone touch test without RF or EEPROM
access. `measurement` is bench firmware, not the normal transmitter application.
Do not substitute these images for normal operation.

[[model-converter]]
== Model storage recovery and converter

Before enabling RF, the main firmware checks the model directory and both banks
of all eight model slots. Native model formats 6 through 9 remain readable.
An unsupported format, unrecoverable model data, a missing required module or an
unfinished conversion/reset blocks normal operation and all model writes.
The LCD shows the reason and, when available, the stored/supported versions:

1. *Off / external conversion* is the default. No model data is changed.
   The i6S releases its power latch; the i6X asks you to use its mechanical switch.
2. *Initialize ALL models* requires a second confirmation, initially set to Cancel.
   This clears all model slots and the directory, then creates a four-channel
   model with no receiver binding and RF OFF. Calibration and transmitter/input
   settings are preserved.

An interrupted reset remains blocked until initialization is explicitly repeated.
Never use an older firmware that ignores the migration marker while recovery is pending.

Each default board build also generates an *English, RF-OFF maintenance image*:
`build-i6x/coretx-i6x-converter.bin` or `build-i6s/coretx-i6s-converter.bin`,
with matching HEX/ELF/resource-report files. These are not operating firmware.

* Back up the *external EEPROM*, not only internal flash.
* Flash the converter matching the transmitter through <<dfu-update,ROM DFU>>.
* Start normally (hold both front power buttons for 3 s on i6S). Inspect source
  versions, target format 9 and model count. Release the controls, then confirm
  with OK (i6X) or the left rear button (i6S); Cancel/right rear cancels.
* Keep power stable until conversion and read-back verification finish.
* Switch off, enter ROM DFU again and flash the matching normal firmware.

The converter upgrades native CoreTX model formats 6/7/8 to 9, preserves model
names, receiver settings and active-model selection, and resumes interrupted
conversion using the journal and migration marker. It does not import Flysky
factory/EdgeTX EEPROMs, repair arbitrary corrupt data or downgrade future formats.
Unknown formats and ambiguous journals are refused without starting conversion.

=== Maintaining storage compatibility

Every model-format change must update the shared codec, converter and independent
historical-version fixtures together. The explicit `converter_target` assertion
and fixture-version manifest prevent an unnoticed format bump from building.
Run `coretx_model_converter`, `coretx_i6x_menu` and `coretx_application` host tests,
including interrupted writes/resets, and build both boards' converter images.
Both firmware workflows build and publish the converter BIN/HEX alongside every
release; the i6X workflow also runs migration/recovery tests with the main tank module OFF.

== Host simulator and tests

The `build` and `sanitize` presets enable the SDL3 simulator:

[source,shell]
----
cmake --preset build
cmake --build --preset build
ctest --preset build
./build/coretx_simulator

cmake --preset sanitize
cmake --build --preset sanitize
ctest --preset sanitize
----

For tests without SDL3, configure with `cmake --preset build -DCORETX_SIMULATOR=OFF`
or the equivalent `sanitize` command. Re-enable the simulator explicitly with
`-DCORETX_SIMULATOR=ON` when needed again.
`sanitize` adds AddressSanitizer and UndefinedBehaviorSanitizer.
Host tests and simulator are not firmware images.

[[web-simulator]]
== Browser simulator

The browser simulator runs the real sender application, menus, calibration and
mixing on virtual i6X/i6S hardware. It combines physical controls, the actual
128x64 LCD framebuffer and 16 output bars. New sessions have a four-channel model
and calibrated virtual controls. The i6S supports LCD touch/mouse gestures and
the real rear-button/pot setup navigation. All RF hardware is simulated.
Stick centering preferences are saved separately per profile; control positions
intentionally start neutral.

Build both profiles with Emscripten 7.x, CMake >= 3.30 and Ninja, then serve them
together over HTTP (not `file://`). These commands use Bash:

[source,shell]
----
for profile in i6x i6s; do
  emcmake cmake -S . -B "build-web-$profile" -G Ninja \
    -DCORETX_WEB=ON -DCORETX_BOARD="${profile^^}" \
    -DTRANSLATION=DE -DCMAKE_BUILD_TYPE=Release
  cmake --build "build-web-$profile" --parallel 2
done
mkdir -p build-web-site
cp platform/web/{index.html,simulator.js,simulator.css} build-web-site/
cp build-web-i6x/coretx-i6x.{js,wasm} build-web-i6s/coretx-i6s.{js,wasm} build-web-site/
python3 -m http.server 8080 --bind 127.0.0.1 --directory build-web-site
----

Open `http://127.0.0.1:8080`. Activate the Emscripten environment first if necessary;
some distributions install its tools in `/usr/lib/emscripten` without updating
`PATH`. This build does not require SDL3.

Each profile automatically saves its native 16-KiB EEPROM image locally after
edits and writes finish, including models, calibration and radio settings.
Concurrent browser tabs cannot silently overwrite a changed saved image.
Download important EEPROMs as files: browser storage is not a backup.
Imports run as a separate test session; the previous browser image is preserved
until explicitly replaced. Unsupported model versions enter firmware recovery
instead of silently resetting data. No model data is uploaded.

Import only complete native CoreTX EEPROM images for the selected board, not
firmware BINs or the old SDL simulator's 1-/2-KiB state files. EEPROM downloads
are *not flashable firmware*. Always calibrate real hardware separately; do not
reuse virtual calibration values on a physical transmitter without verification.

The `Browser simulator` Action builds/tests both profiles on pushes/PRs and
uploads a website artifact. Version tags (`v...`) and manual runs additionally
deploy to GitHub Pages. The same version tags build the firmware and attach
`coretx-browser-simulator.zip` to the shared GitHub release. Extract the ZIP and
serve it over HTTP; do not double-click `index.html`.
First select *GitHub Actions* in the repository's
*Settings -> Pages -> Build and deployment -> Source*, and allow release tags
in the `github-pages` environment if required.
The deployment URL is `https://wimalopaan.github.io/CoreTx/`.

CTest includes the native engine tests. Run `node --test tests/web_controls_test.mjs`
and `node tests/web_wasm_test.mjs build-web-i6x build-web-i6s` for the frontend
helpers and compiled modules. CI additionally exercises the actual website
using Playwright/Chromium.

== Presets and CMake options

[cols="1,2,3",options="header"]
|===
|Preset |Directory |Configuration
|`build` |`build/` |Native Debug, simulator ON, sanitizers OFF.

|`i6x` |`build-i6x/` |ARM GCC, MinSizeRel, STM32 firmware, FS-i6X.

|===

Configure presets and build presets have the same names.
CTest presets exist for `build` and `sanitize`.
The following are project options and their defaults when not overridden by a preset/cache:

[cols="2,1,4",options="header"]
|===
|Option |Default |Effect
|`CORETX_SANITIZERS` |`OFF`
|Host ASan/UBSan with GCC/Clang; incompatible with STM32 firmware.
|`CORETX_SIMULATOR` |`OFF`
|POSIX SDL3 desktop simulator; enabled by the native presets.
|`CORETX_WEB` |`OFF`
|Emscripten browser simulator; a separate build directory per `CORETX_BOARD`.
|`CORETX_STM32F072` |`OFF`
|Bare-metal ARM firmware; enabled by the board presets, requires the ARM GCC toolchain.
|`CORETX_ADC_COHERENT_SNAPSHOTS` |`OFF`
|i6X firmware only: use two DMA halves for coherent ADC snapshots, at extra RAM cost.
 Does not enable this mode on i6S firmware.
|`CORETX_A7105` |`ON`
|Internal A7105/AFHDS 2A support.
|`CORETX_CRSF` |`ON`
|External UART CRSF support.
|`CORETX_MULTISWITCH` |`ON`
|MultiSwitch dashboards and SET4 commands; effective only with `CORETX_CRSF=ON`.
|`CORETX_MODUL_TANKMIX` |`ON`
|Compile the tank mixer, its configuration UI and internal direction conditions.
 With `OFF`, models using the module are rejected and writes are blocked rather
 than falling back to different channel behavior. Inactive module settings
 remain in the storage format for lossless roundtrips.
|`CORETX_EXTENDED_INPUTS` |`ON`
|Compile additional analog/digital input support.
 Individual expansion inputs still default to Off in radio setup.
|`CORETX_SECURE_UI` |`OFF`
|Require RF off for protected UI operations.
 Hardware ownership and storage safety interlocks remain active even when OFF.
|`CORETX_I2C_FAST_MODE` |`ON`
|EEPROM I2C2 at approximately 400 kHz; OFF selects 100 kHz.
 Does not change the i6S touch bus.
|`CORETX_CRSF_REMOTE_TIMEOUT_MS` |`1000`
|CRSF parameter read timeout per request for receivers and other devices behind the RF link,
 100..10000 ms. The TX module itself keeps 500 ms.
|`CORETX_CRSF_REMOTE_RETRIES` |`9`
|Repetitions of an unanswered remote parameter read, 0..50. The default gives
 10 requests, so _CRSF response timeout #n_ appears after about 10 s.
 The TX module itself keeps 2 repetitions.
|`CORETX_CRSF_PARAMETER_IDS` |`256`
|Highest CRSF parameter ID + 1 that the menu can hold, 32..256. Costs five bytes of RAM per ID;
 devices with higher IDs report _CRSF memory limit_. 256 covers every device.
|`CORETX_CRSF_CACHE_BYTES` |`1280`
|RAM cache for loaded CRSF parameter entries, 512..4096 bytes. Smaller caches reload
 parameters more often while scrolling but limit nothing else.
|`CORETX_I6S_TOUCH_THRESHOLD` |`22`
|i6S FT6236 touch threshold (register 0x80), 10..60; lower is more sensitive.
 See _Touch sensitivity_ in PERIPHERALS.adoc.
|`CORETX_BOARD` |`I6X`
|Board selection: `I6X` or `I6S`; the i6s preset selects `I6S`.
 Also selects board features in native tests.
|`TRANSLATION` |`EN`
|Native UI language: `EN` or `DE`. Board firmware targets always generate both languages.
|`CORETX_EDGETX_SOURCE` |empty
|Optional local EdgeTX checkout for the original-source comparison test.
 Not needed to build CoreTX.
|===

`CORETX_I6S` is derived from the board selection; it is not a user-facing option.
Relevant standard CMake settings:

[cols="2,4",options="header"]
|===
|Setting |Use
|`BUILD_TESTING` |ON by default for host builds; disable to omit tests.
 Firmware configuration returns before CTest is included.
|`CMAKE_BUILD_TYPE` |Debug in native presets, MinSizeRel in firmware presets.
|`CMAKE_TOOLCHAIN_FILE` |`cmake/arm-none-eabi-gcc.cmake` in firmware presets.
 Select a toolchain when creating a build directory, not after configuring a different compiler.
|`CMAKE_CXX_COMPILER` |Select the native compiler on first configuration.
 Firmware requires ARM GCC.
|===

Set options at *configure time*, not on `cmake --build`:

[source,shell]
----
cmake --preset i6s -DCORETX_A7105=OFF -DCORETX_SECURE_UI=ON
cmake --build --preset i6s
----

To disable CRSF and its dependent MultiSwitch support, configure with
`-DCORETX_CRSF=OFF`. To retain CRSF but omit MultiSwitch, use
`-DCORETX_MULTISWITCH=OFF`.
An option enabling compiled support does not activate RF or assign physical inputs.
For example, the runtime *External module* setting controls whether i6S PB6/PB7
belong to CRSF or expansion switches.

Explicit `-D` values persist in that build directory's cache until changed.
Reconfigure and rebuild each affected board separately.

[[offline]]
=== CMSIS without downloads

The pinned dependency definitions are in `cmake/cmsis.cmake`.
Use matching local checkouts with standard FetchContent overrides:

[source,shell]
----
cmake --preset i6s \
  -DFETCHCONTENT_SOURCE_DIR_CORETX_CMSIS_CORE=/path/to/CMSIS_6 \
  -DFETCHCONTENT_SOURCE_DIR_CORETX_CMSIS_F0=/path/to/cmsis-device-f0
----

The first directory must contain the CMSIS core headers, the second the STM32F0
device headers. These overrides apply to host hardware tests as well.

== Flash preparation and backups

WARNING: Disconnect motors/remove propellers. Use a stable supply, the correct
board image and a USB data cable. Flashing replaces the original application.
These are STM32F072 128 KiB images, not firmware for other Flysky transmitters.

Enter the STM32 *ROM DFU bootloader* using the procedure appropriate for the exact
transmitter/PCB revision. CoreTX does not implement a USB DFU runtime reboot;
normal USB operation is not evidence that ROM DFU is active.
Verify that the device identifies as *`0483:df11`* before writing.
Connect only the intended DFU device.

Back up the original 128 KiB internal flash before replacement, using one of the
read commands below. The *external I2C EEPROM is separate*: a DFU flash backup does
not include models, calibration or radio settings.
Preserve an external EEPROM backup separately before firmware/storage migration.
Do not use mass-erase or read-protection removal as a routine flashing step;
unprotecting can erase existing data.

[[first-flash]]
=== First installation from factory firmware

The first installation needs *hardware entry into ROM DFU*, before any CoreTX
code is running. The documented boards use these temporary boot-selection bridges:

[cols="1,1,3",options="header"]
|===
|Board |Bridge |Reference
|FS-i6X |*R53 pads*
|https://github.com/OpenI6X/opentx/wiki/Flashing-%26-Upgrading[OpenI6X flashing guide]
 and https://github.com/OpenI6X/opentx/blob/master/doc/flysky/dfu_jump_r53.jpg[PCB photo].
|FS-i6S |*R60*
|https://fishpepper.de/2016/09/15/openground-part-2-fs-i6s-dfu-bootloader-access/[OpenGround DFU guide]
 and https://fishpepper.de/2016/09/15/openground-part-1-components-pinout/[PCB/pinout reference].
|===

These are different boards: *R53 on i6X, R60 on i6S*.
The procedures do *not* require desoldering a resistor.
Check the markings and the referenced PCB photographs against your revision.
If the layout differs or the pads cannot be identified confidently, stop rather
than shorting an assumed component.
Do not leave a permanent boot bridge installed.

[[first-flash-i6x]]
==== FS-i6X: bridge R53

1. Switch off, disconnect USB and remove the batteries. Open the housing carefully;
   do not pull on wires between its halves.
2. Locate the two R53 pads shown in the reference photo and install a temporary,
   secure bridge without contacting adjacent pads.
3. Reconnect the batteries and USB data cable, then turn the mechanical power switch on.
4. The display stays blank. Confirm *STM32 BOOTLOADER / `0483:df11`* on the PC.
   If it does not appear, do not flash; check bridge position, power, cable and driver.
5. Back up the entire internal flash first, then write the *i6X* CoreTX BIN using
   one of the methods below. Preserve an external EEPROM backup separately.
6. Switch off and disconnect USB/batteries before removing the bridge.
   Inspect the PCB, reassemble and boot normally without the R53 bridge.

[[first-flash-i6s]]
==== FS-i6S: bridge R60

1. Disconnect USB and remove the batteries. Open the housing carefully, respecting
   the wires between its halves.
2. Identify R60 using the board reference and make a temporary, secure bridge;
   do not bridge neighboring components.
3. Reconnect the batteries. Hold *both front power buttons for about 5 s*,
   then connect the USB data cable, maintaining power during the transition.
   This is the ROM-entry procedure, not CoreTX's normal shutdown gesture.
4. The LCD/backlight remains off. Confirm *STM32 BOOTLOADER / `0483:df11`*.
   Keep USB power stable throughout backup and flashing: ROM DFU does not run
   CoreTX's PB15 power-latch handling.
5. Back up the entire internal flash first, then write the *i6S* CoreTX BIN using
   one of the methods below. Preserve an external EEPROM backup separately.
6. Disconnect all power before removing the temporary R60 bridge.
   Inspect the PCB, reassemble and start normally with both power buttons.

If `:leave` does not produce a normal start while a bridge is installed, complete
the power-off/bridge-removal procedure before trying a normal boot.
Do not force these STM32 commands onto a different MCU/USB ID; compatibility with
APM32 clone variants is not established by this guide.

[[dfu-update]]
=== Subsequent updates and recovery

After installing a CoreTX build with power-on DFU support, no opening or boot
bridge is needed for routine updates:

[cols="1,3",options="header"]
|===
|Board |Hold while switching on
|FS-i6X |Both *horizontal trim buttons inward*: left horizontal trim to the right,
 right horizontal trim to the left. The combination is independent of stick mode.
|FS-i6S |Both *rear buttons SE/SF* (PA9/PA10), then hold both front power buttons for 3 s
 for normal power-on. The rear buttons are not the front power buttons.
|===

1. Switch off and unplug USB first so the MCU actually loses power.
2. Hold the board's combination *before* reconnecting USB/applying power.
   Turn on using the normal power switch/buttons and keep the combination held
   until *STM32 BOOTLOADER / `0483:df11`* appears.
3. Release the keys, keep power/USB stable, and write the matching board BIN
   using Web Flasher, `dfu-util` or `rdfu` below.
4. After flashing, restart normally with the DFU keys released.

CoreTX samples and debounces the keys at cold startup, keeps RF off and enters the
STM32 ROM bootloader *before starting the watchdog or accessing EEPROM*.
On i6S the PB15 power latch remains active during handoff.
The LCD displays `DFU-Bootloader` before the handoff and retains the message in ROM DFU.
Hardware boot-pin entry bypasses CoreTX and cannot display this message.
The same combination works in the i6S touch-trace, standalone touch-diagnostic
and measurement images.
Watchdog/software resets deliberately do not use this shortcut: an already
running watchdog cannot be stopped for a reliable DFU session.

Normal i6S cold startup also requires both front power buttons to be held continuously
for 3 s. Releasing either button restarts the delay; RF and the LCD remain off until
the delay has elapsed. Watchdog/software resets do not repeat the power-on delay.

This is a jump into the MCU's ROM, not a separate CoreTX flash bootloader or a
USB runtime reboot command. Factory firmware, older CoreTX builds without this
feature, or a damaged application still require the <<first-flash,hardware DFU
procedure>>. Keep R53/R60 unbridged during normal operation.

Writing CoreTX at `0x08000000` replaces the flash-resident Flysky application/
updater bootloader. The stock Flysky updater is not the CoreTX update method.
The separate STM32 ROM bootloader remains accessible through the hardware
boot selection. To restore stock firmware, write the saved complete flash image
through ROM DFU and restore the corresponding external EEPROM separately.
After a first installation, calibrate controls and verify the model, output
directions and failsafe with RF/motors safely disabled; foreign EEPROM layouts
are not interchangeable with CoreTX records.

=== Ferrox Web Flasher

Open https://ferroxrc.com/flasher in Chrome, Edge or Brave with WebUSB support.
Choose the matching transmitter and load the locally built/downloaded CoreTX
`.bin` as a *local file*. Do not select an offered Ferrox release instead.
Connect the ROM DFU device, authorize browser USB access and complete the write.
Use the board's normal boot procedure afterward.

Windows needs a suitable driver for *STM32 BOOTLOADER*, for example WinUSB via
Zadig. Linux needs USB permissions; on a systemd-logind desktop a local udev rule
can grant access to the active user:

[source]
----
SUBSYSTEM=="usb", ATTR{idVendor}=="0483", ATTR{idProduct}=="df11", TAG+="uaccess"
----

Install the rule in `/etc/udev/rules.d/` with administrator rights, reload rules
and reconnect the device. Follow local policy on other systems.
macOS needs a WebUSB-capable browser but no separate STM32 driver.

=== dfu-util

Install https://dfu-util.sourceforge.net/[dfu-util] for your OS
(for example the `dfu-util` package on Debian/Ubuntu).
These examples use an i6S English image; use
`build-i6x/coretx-i6x-en.bin` for an i6X, or the corresponding `-de.bin`.

[source,shell]
----
dfu-util -l
dfu-util -d 0483:df11 -a 0 -s 0x08000000:131072 -U original-firmware.bin
dfu-util -d 0483:df11 -a 0 -s 0x08000000:leave -D build-i6s/coretx-i6s-en.bin
----

The read command backs up internal flash; `-D` writes the raw BIN and `:leave`
requests exit from DFU. Confirm that alternate setting 0 is internal flash in
the listing. If the device remains in DFU, use the normal boot procedure.

=== rdfu (EdgeTX/rs-dfu)

Use the `rdfu` command-line tool from
https://github.com/EdgeTX/rs-dfu[EdgeTX/rs-dfu].
Download the matching OS/architecture CLI binary from its
https://github.com/EdgeTX/rs-dfu/releases[releases], make it executable where
required, and place it on `PATH` as `rdfu` (or use its full filename).
Rust/Cargo is needed only if building this utility from source.

[source,shell]
----
rdfu list --vendor 0483 --product df11
rdfu read --vendor 0483 --product df11 --start-address 0x08000000 --length 131072 original-firmware.bin
rdfu write --vendor 0483 --product df11 --start-address 0x08000000 build-i6s/coretx-i6s-en.bin
----

CoreTX supplies raw BIN images, so the start address is explicit.
Use the board's normal boot procedure after a successful write.
`rdfu reboot` targets an EdgeTX bootloader mechanism; it is not a CoreTX command
for entering the STM32 ROM bootloader.

== Published images

https://github.com/wimalopaan/CoreTx/releases[CoreTX releases] may lag the source
version. The workflows `.github/workflows/i6x.yml` and `.github/workflows/i6s.yml`
build the respective board's German/English firmware on pushes, pull requests
and manual runs. Version tags matching `v[0-9]*` attach both boards' DE/EN BIN/HEX
and converter assets to the same GitHub release. `.github/workflows/web.yml` builds
the browser simulator from the same tag and publishes `coretx-browser-simulator.zip`
alongside the firmware, plus the Pages website.
Artifact names and filenames are board-specific;
rerunning one board's workflow does not remove the other board's assets.
Build locally when no matching release image exists.

For electrical assignments and resource conflicts, see
link:PERIPHERALS.adoc#i6x[FS-i6X peripherals] and
link:PERIPHERALS.adoc#i6s[FS-i6S peripherals].
